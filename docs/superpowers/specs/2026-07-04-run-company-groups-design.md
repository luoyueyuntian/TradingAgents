# 运行记录按公司分组与分页设计

## 背景

当前运行记录页使用扁平的运行列表接口，前端直接把 `RunSummary[]` 渲染成单张表格。最近已经为运行记录补齐了 `company_name`，但新的产品目标不再只是多显示一列，而是要：

- 按公司对运行记录分组
- 按每家公司最近一次分析时间倒序排序
- 为后续“按公司组分页”保留稳定的接口结构

如果继续沿用“前端拿到扁平运行列表后自行分组”的方案，分页上线后同一家公司会被切散到不同页，分组体验会失真，因此需要把“公司组”提升为后端接口的一等数据结构。

## 目标

- 新增一个按公司分组的运行记录接口
- 分页单位是“公司组”而不是单条运行记录
- 公司组按最近一次分析时间 `latest_created_at` 倒序排序
- 每个公司组返回最近 `5` 条运行记录，同时带该公司的总运行数
- 运行记录页改成公司卡片列表，消费新的分组分页接口

## 非目标

- 不修改现有扁平 `GET /api/runs` 的返回结构
- 不修改运行记录 CSV 导出格式
- 不在本次实现中加入“展开更多组内运行记录”
- 不补做历史旧运行的公司名迁移

## 方案概览

### 保留扁平接口

现有 `GET /api/runs` 继续返回扁平 `RunSummary[]`，供运行详情页和其他依赖旧结构的页面继续使用。

### 新增按公司分组接口

新增一个公司分组专用接口，例如：

`GET /api/runs/company-groups`

该接口支持以下查询参数：

- `q`
- `status`
- `archived`
- `page`
- `page_size`

其中分页参数的语义为：

- `page`：从 `1` 开始的页码
- `page_size`：每页返回多少个公司组

### 后端处理顺序

后端对公司分组接口的处理顺序固定为：

1. 先复用现有运行筛选逻辑，得到过滤后的运行列表
2. 对过滤后的运行列表按公司分组
3. 对每个公司组内部的运行按 `created_at` 倒序排序
4. 计算每个公司组的聚合字段
5. 按公司组的 `latest_created_at` 倒序排序
6. 最后再对公司组做分页

这样可以保证：

- 当前筛选条件只影响可见公司组
- 同一家公司不会被同一页切散
- 以后继续增强分页时不需要改语义

## 分组规则

### 分组键

公司组的分组键不只依赖 `company_name`，而是使用：

- 规范化后的 `company_name`
- `asset_type`

当 `company_name` 为空时，回退到 `ticker + asset_type`。

这样做的原因是：

- 历史旧运行可能没有 `company_name`
- 极少数情况下不同资产类别可能出现相同展示名
- 只按公司名分组会让兼容和冲突处理更脆弱

### 公司组展示字段

每个公司组包含：

- `group_key`
- `company_name`
- `asset_type`
- `tickers`
- `run_count`
- `latest_run_id`
- `latest_status`
- `latest_signal`
- `latest_date`
- `latest_created_at`
- `recent_runs`

其中：

- `company_name` 用于前端卡片标题展示
- `tickers` 用于兼容一个公司可能出现多个 ticker 的情形
- `run_count` 表示该公司在当前筛选条件下命中的总运行数
- `recent_runs` 只返回最近 `5` 条运行记录

## 接口返回结构

建议新增两个 schema：

- `RunCompanyGroup`
- `RunCompanyGroupPage`

返回结构示意如下：

```json
{
  "items": [
    {
      "group_key": "apple-inc-stock",
      "company_name": "Apple Inc.",
      "asset_type": "stock",
      "tickers": ["AAPL"],
      "run_count": 12,
      "latest_run_id": "run-123",
      "latest_status": "completed",
      "latest_signal": "Buy",
      "latest_date": "2026-07-04",
      "latest_created_at": "2026-07-04T13:00:00",
      "recent_runs": [
        {
          "run_id": "run-123",
          "ticker": "AAPL",
          "company_name": "Apple Inc."
        }
      ]
    }
  ],
  "page": 1,
  "page_size": 20,
  "total_count": 87
}
```

`total_count` 表示公司组总数，而不是运行记录总数。

## 前端展示

运行记录页改成“公司卡片列表”。

### 页面结构

- 顶部筛选区保留现有 `q / status / archived`
- 主体区域渲染公司组卡片列表
- 每个卡片顶部显示：
  - 公司名
  - 最近分析时间
  - 总运行数
- 每个卡片内部展示一个小表格，只列出该公司最近 `5` 条运行记录
- 页面底部增加分页控件，翻页对象是公司组

### 交互规则

- 页面初始化请求第一页公司组
- 任一筛选条件变化时，重置到第一页并重新拉取公司组
- 点击组内某条运行记录时，继续跳转现有运行详情页
- 如果公司名为空，卡片标题回退到 ticker 或组合后的显示名

## 兼容性

### 与现有页面兼容

`RunDetailPage.vue` 等仍依赖扁平 `/api/runs` 的页面不需要改接口，只继续走旧路由。

### 与历史数据兼容

旧运行如果缺少 `company_name`：

- 分组时回退到 `ticker + asset_type`
- 展示时使用 ticker 作为标题兜底

这样可以避免历史数据直接消失或被错误合并。

## 错误处理

- `page < 1` 时返回校验错误
- `page_size < 1` 时返回校验错误
- 可以为 `page_size` 设上限，例如 `100`，防止单次响应过大
- 如果请求页超出总页数，返回空 `items`，但保留正确的 `total_count`

## 测试

### 后端

- 路由测试：公司组按 `latest_created_at` 倒序返回
- 路由测试：同公司的 `recent_runs` 按 `created_at` 倒序返回
- 路由测试：分页按公司组而非运行记录生效
- 路由测试：每个公司组只返回最近 `5` 条运行记录，但 `run_count` 仍是完整计数
- 路由测试：旧数据无 `company_name` 时按 ticker 回退分组

### 前端

- 页面源码测试：运行记录页改为公司卡片列表而不是单一扁平大表
- 页面逻辑测试：筛选变化会重置到第一页
- 页面逻辑测试：分页请求命中新的公司组接口
- 页面结构测试：组内行点击仍跳转运行详情页

## 风险与约束

- 同一公司历史上可能出现多个 ticker，因此分组输出需要保留 `tickers`
- 如果以后要支持“展开更多组内运行记录”，最好再单独增加组内详情接口，而不是直接把当前分页接口改成返回全部运行
- 这次先限制每组只返回最近 `5` 条记录，是为了控制响应体积并给分页稳定性留余地
